# Rolf: второй источник данных + сравнение по источникам

Дата: 2026-09-05
Статус: Дизайн утверждён владельцем в брейнсторме
Расширяет: раздел T2 в `2026-09-05-auto-analytics-database-design.md` (T1 завершён и закоммичен)

## Контекст

T1 завершён: `auto-analytics` читает данные из PostgreSQL через Express API, схема multi-source готова:

- `offers.source` (`'major-expert' | 'rolf'`), `UNIQUE(source, source_id)`, запись per-источник через `applySync(pool, { source, cars, today, deactivate })`.
- `/api/offers?source=&brand=&yearFrom=&yearTo=` , `/api/history?source=` , `/api/meta` уже поддерживают `source`.
- Дашборд грузит все активные предложения в память (`fetch('/api/offers')`) и фильтрует на клиенте.
- Парсер major-expert: `scraper/index.js`, в существующем крон-workflow `scrape-daily.yml`.

Основано на брейнсторме с владельцем:
1. Полный снэпшот б/у-авто Москвы с rolf.ru («все б/у»), не только пересечение с major-expert.
2. Матчинг «того же авто» — строгий ключ: `норм(brand) + норм(model) + year + engine_volume`; нормализация названий моделей по словарю.
3. Блок сравнения — отдельная секция «Сравнение источников» (список пар, две колонки).
4. Патч матчинга — клиентский утилит (без миграций схемы и без нового endpoint).

## Цели

1. Новый источник: все б/у-объявления rolf.ru в Москве попадают в `offers` (`source='rolf'`) ежедневным cron.
2. Фильтр «Источник» в дашборде: Все / major-expert / rolf — влияет на списки, графики и PriceHistoryChart.
3. Секция «Сравнение источников»: авто, присутствующие на обоих сайтах, с краткой сравнительной характеристикой.
4. Дашборд/API остаются отзывчивыми при десятках тысяч объявлений.

## Дизайн

### 1. Write-сторона: парсер rolf.ru

**Спайк (первая задача плана).** Утвердить способ получения б/у-объявлений rolf.ru Москвы:

- Проверить `apiweb.rolf.ru` (preconnect в HTML лендинга) и бандл `/tmp/rolf_nuxt.js`: найти XHR-endpoint списка б/у с фильтром «с пробегом» и городом; определить метод, параметры, пагинацию, поля, лимиты.
- Если JSON-endpoint ненадёжен/закрыт — запасной вариант: HTML/Sitemap `https://www.rolf.ru/cars/used/` и `/__sitemap__/msk/listing-used.xml` через cheerio.
- На выходе спайка — репорт: способ запроса, URL, пример ответа (фикстура), количество объявлений, оценка страниц по Москве. Фикстура реального ответа сохраняется в `test/fixtures/` для юнит-тестов.

**Парсер `scraper/rolf.js`** — по образцу `scraper/index.js`:

- Пагинация, задержка 300мс, браузерный UA, таймаут 15с, CLI `--pages=N` для тестов.
- Retry-паттерн T1: 1 попытка повтора на страницу, `ok`-флаг, счётчик упавших страниц, при частичном прогоне `applySync(..., { deactivate: false })` и WARNING. Поведение «детализированного» прогона: при успехе всех страниц — обычная деактивация per-источника.
- Нормализация в ту же схему `offers` с `source: 'rolf'`: brand, model, year, mileage, body_type, fuel_type, engine_volume, horsepower, transmission, drive_type, color, price, old_price, url, image, owners (null, если API не отдаёт), `is_new=false` (только «с пробегом»).
- Запись через существующий `scraper/db.js` (`applySync`), без изменений схемы.
- Ежедневный cron: в `scrape-daily.yml` после major-expert — `node scraper/index.js && node scraper/rolf.js`. Ошибочный rolf-прогон не роняет major-expert (два отдельных шага job).

### 2. Read-сторона: объём, фильтр источника

Объём: полный снапшот б/у Москвы (~десятки тысяч объявлений). Удовлетворённость при этом объёме:

- `/api/offers?limit=` — параметр из исходного дизайна (`2026-09-05-auto-analytics-database-design.md`, эндпоинт `/api/offers`); без `limit` возвращаются все активные.
- Трешинг точек скаттера «Пробег vs Цена» на клиенте: выборка до ~2000 точек суммарно с сохранением группировки по маркам (топ-7 + «Другие»); трендовые линии строятся по этому же подмножеству.
- Фильтр «Источник» в панели фильтров: `Все / major-expert / rolf`. Применяется к спискам, графикам, секции сравнения и к `/api/history?source=` (PriceHistoryChart).
- Заголовок/подпись дашборда: количество объявлений счётчика пересчитывается по активному источнику.

История цен: `price_history` растёт ~50k строк/день (одна строка на объявление). Для сдерживания:

- `/api/history?days=N` — окно истории, по умолчанию 90 дней; даты/агрегат ограничиваются.
- Ретеншн в cron-шаге перед парсингом: `DELETE FROM price_history WHERE date < CURRENT_DATE - 90`. Порог 90 совпадает с дефолтом окна `/api/history`.

### 3. Матчинг и секция «Сравнение источников»

**Утилит `src/utils/matchCars.js`** (чистый, без React):

- `normalizeBrand`, `normalizeModel`: lowercase, схлопывание пробелов, удаление служебных знаков, словарь алиасов (варианты написания одной модели на двух площадках — калибруется на выборке из спайка).
- `matchKey(car)`: `норм(brand) + '|' + норм(model) + '|' + year + '|' + engineVolume`. Строгое равенство.
- `findMatches(cars)`: группировка по ключу; возвращает пары, где в группе присутствуют минимум два разных `source`. Пары детализированы: характеристики с каждого источника. Поведение при `engineVolume`/`year` null: в матчинг не входят.
- Не матчит одно и то же объявление источника с самим собой (группа из одного источника не считается парой).

**Секция «Сравнение источников»** в `src/App.jsx` (ниже «Лучших предложений»):

- Список пар из текущих отфильтрованных данных (уважает фильтры: обе стороны пары должны проходить действующие фильтры).
- Каждая пара — две колонки (major-expert / rolf): цена, пробег, год, объём, КПП, привод, цвет, owners (если есть), ссылка на сайт. Поле, отсутствующее у источника — «—».
- Highlight: у кого цена ниже — подсветка; у кого пробег ниже — подсветка.
- Заголовок с количеством найденных пар; пустое состояние «Нет авто, встречающихся на обоих источниках».

### 4. Тестирование и приёмка

- Юнит `src/utils/matchCars.js`: нормализация (фикстуры реальных названий обеих площадок); строгий ключ не даёт ложных срабатываний; null year/engineVolume исключены; группа одного источника не пара; алиасы матчатся.
- Юнит нормализации rolf-ответа → строка `offers` (фикстура реального ответа).
- Интеграция `test/db.test.js`: синк второго источника в ту же БД (source 'rolf', `UNIQUE(source, source_id)` без конфликтов); per-source деактивация при смене состава между прогонами.
- API: `/api/offers?source=rolf&limit=N`; `/api/history?days=N`.
- Вит `src/App.test.jsx`: фильтр источника переключает данные; секция сравнения рендерит пары и уважает фильтры.
- Ручная приёмка на сервере: полный прогон rolf-скрапера на `auto_analytics_test` (`0 deactivated`, счётчики, оценка объёма); UI-проверка секции сравнения на реальных данных.

## Что вне скоупа

- Мягкий/толерантный матчинг (по пробегу/цене) — только строгий ключ.
- `match_key` в БД и эндпоинт `/api/matches` (патч B).
- Кликабельность точек скаттера и деталка объявления.
- Матчинг «новых» авто (новые не входят — ролф только «с пробегом»).
- Owners в карточках (это T3), соединение со сравнением — по факту наличия поля.

## Риски

- rolf-API изменится или закроется (антибот) — парсер изолирован (`scraper/rolf.js`), менять его точечно; запасной path — cheerio.
- Названия моделей на площадках расходятся сильнее, чем ожидалось — словарь алиасов калибруется на спайке; при дефиците совпадений словарь расширяется, правило ключа не меняется.
- Объём неизвестен до спайка: если полный снэпшот Москвы > ~50k — пересмотреть лимиты `/api/offers`, трешинг и ретеншн, не меняя контракты.
- Рост `price_history`: ретеншн 90 дней ограничивает рост; превышение объёма/скорости записи пересматривается после первого реального прогона.
